# HACKTALE 公演予約システム（/hacktale/reservation・/hacktale/admin）

HACKTALE公式サイトの公開公演予約。お客様が作品・公演日時・人数を選んで申し込むと
予約が確定し、人数分の残席が減る。決済は含まない（料金・支払い方法は公演ごとに
文言で設定して予約画面とメールに表示する）。

**/yoyaku（日程調整）と同じ無料インフラで動く。追加契約は不要。**

## 画面（2026-09-27 改修）

- **予約ページ** `/hacktale/reservation/`: 月カレンダー（各日に開始時刻と「残○」、満席は赤）＋日付ごとの公演カード。
  受付中の公演はカレンダーからそのままフォームへ。作品・形式（対面/オンライン）で絞り込み（`?work=` `?fmt=`）、月送りは `?m=YYYY-MM`。
  スマホではカレンダーのマスに作品名を出さず（時刻と残席のみ）、下の日付別カードで作品を確認する。
- **管理画面トップ**: 公演回ごとに予約メーター（予約/最少/定員）と予約者一覧（お名前・人数・電話・メール・X・備考・予約日時・メール状況）を展開表示。
- **作品の対応形式**: 作品ごとに「対面公演あり／オンライン公演あり」と形式ごとの料金を持つ。**人狼定理は両方**（対面4,500円・オンライン3,500円）。
  公演回の作成時は形式の選択が必須で、作品が対応していない形式は作れない。受付メールの「流卓連絡1週間前」は人狼定理なら形式を問わず入る（公演回ごとに直せる）。

## 開催の流れ（2026-09-27 改修：立卓／流卓）

HACKTALE の公演は「最少人数が集まったら開催」なので、予約＝即開催ではない。

1. **申し込み** → ①受付メール「開催人数に達しましたら改めてご案内」（流卓連絡は前日20時頃、人狼定理は1週間前）
2. **開催決定（立卓）** → ②開催案内メール（日時・料金・会場・支払い・規約）を確定予約の全員へ
   - 対面: 「自動開催決定」ON（既定）なら、最少人数に達した申し込みの時点で自動で開催決定＆一斉送信
   - オンライン: 自動OFF（既定）。公演回に **Discordリンク** を入れてから管理画面の「開催決定」→ 文面を確認して一斉送信
   - 開催決定後に申し込んだ人には、受付メールではなく開催案内が自動で届く
3. **開催見送り（流卓）** → 「開催見送り」ボタンで受付停止＋③見送りメールを確認して送信（一覧には「開催見送り」と表示）
4. 毎朝9:10の定期実行で、**開催決定済みの公演だけ**にリマインド。同時に「まだ開催決定していない8日以内の公演（予約数／最少人数）」を管理者にメールで知らせる

### メール文面（公演回ごとに手直し可）

- 公演回を作ると、形式に合わせた既定文面（①受付・②開催案内・③見送り）がコピーされ、公演回の編集画面で自由に直せる。正本は `src/lib/hacktaleTemplates.ts`。
  - ②開催案内の既定は3種類: 対面／対面＋事前読み込み（Discordサーバー案内つき）／オンライン（振込・Discord）。「文面を既定に戻す」で切り替え可
- 差し込み（送信時に自動置換）: `{作品名}` `{日時}` `{日付}` `{開始時刻}` `{料金}` `{お名前}` `{人数}` `{予約番号}` `{Discordリンク}` `{振込先}`
- 宛名「〇〇 様」と、末尾の予約番号・問い合わせ先（info@kabuexlabs.com）は自動で付く
- `{Discordリンク}` `{振込先}` が未入力のままでは開催案内を送れない（画面に警告、自動開催決定も止まり管理者に通知）
- **振込先の口座情報はリポジトリ（GitHubで公開）に置かず、管理画面トップの「設定」に保存**する（KV `ht:settings.bankInfo`）
- 対面の開催案内の会場住所（神田三崎町）は文面に直接書いてある。会場が変わるときは公演回の文面を直す

## セットアップ（既に /yoyaku を運用中なら追加作業はほぼゼロ）

1. **データベース・メール・CRON_SECRET は既存の環境変数をそのまま共用**（`KV_REST_API_URL` / `KV_REST_API_TOKEN` / `SMTP_USER` / `SMTP_PASS` / `CRON_SECRET`）。
2. 管理ページの合言葉は `YOYAKU_ADMIN_KEY` を流用。分けたい場合だけ `HACKTALE_ADMIN_KEY` を設定。
3. デプロイすると cron（毎日9:10 JST）が自動で有効になる。
4. 初回に `/hacktale/admin/` を開くと、サイト掲載中の3作品（プレゼント・ポーカー／人狼定理／ダイスボックス）が自動登録される。

## データ構造（Upstash、プレフィックス `ht:`）

- `ht:works`（hash）… 作品。標準の定員・料金の初期値は「公演回作成時にコピー」される
  だけなので、作品側を変えても登録済みの公演回は変わらない。
- `ht:sessions`（hash）… 公演回。状態は draft（非公開）/ open（公開）/ closed（受付停止）/ cancelled（中止）。
- `ht:res:<公演回ID>`（hash）… 予約。キャンセルしても履歴として残る。
- `ht:seats:<公演回ID>` … 確定人数カウンタ。**予約の作成・人数変更・キャンセルは
  Lua スクリプト（EVAL）で人数チェックと書き込みを1コマンドに）まとめており、
  残り1席への同時申し込みでも定員を超えない。** 管理画面の「確定人数を再集計」で
  予約レコードから作り直せる（整合性の保険）。
- `ht:idem:<トークン>` … 二重送信防止（確認画面ごとに発行、24時間で自動消滅）。
  連打・再送信は最初に確定した予約の完了画面に流れ、新しい予約は作られない。
- `ht:settings` … リマインドの有効/無効と送信タイミング、振込先。
- `ht:golock:<公演回ID>` … 開催決定の排他（同時に最少人数へ達しても一斉送信は1回）。
- `ht:gomail:<予約番号>` … 開催案内の送信権（自動と手動が重なっても1人1通）。
- `ht:maillog` … 送信履歴（直近500件）。
- `ht:rl:<IP>` … 申し込みのレート制限（1時間20件）。

## 残席と受付状態

残席 ＝ 公演回の定員 −（確定済み予約の合計人数）。表示は
「受付中：残り○席」「満席」「受付終了」（受付停止・期限切れ・開始後）「公演中止」。
満席・受付終了・中止はフォーム側とAPI側の両方で申し込みを拒否する。
確認画面を開いただけでは席を確保せず、確定時に残席を再確認する。

## メール

- **受付・開催案内・見送り**: 上の「開催の流れ」を参照。新しい予約のたびに管理者
  （`YOYAKU_ADMIN_EMAIL`）にも通知が届き、最少人数に達したら「開催決定を押してください」と入る。
- **リマインド**: 毎朝9:10 JST の cron で「開始まで◯時間以内」（既定36時間＝実質前日朝）
  の**開催決定済み**公演の確定予約に送信。`remindedAt` を記録するので二重送信されない。
  設定時刻を過ぎてから入った予約は最初から対象外（完了メールのみ）。
  キャンセル済み予約・中止公演には送らない（送信直前に最新状態を再確認）。
  無効化・時間変更は管理画面の「リマインドメール設定」。各公演の「今すぐ送信」で手動送信も可。
- **変更・中止の案内**: 日時/会場を変更、または中止にすると、確定予約への影響が表示され、
  ひな形入りの案内メールを確認してから一斉送信できる。
- 送信に失敗しても予約は保持され、管理画面に「失敗」と表示されて再送できる。
  送信履歴は各公演の画面に出る。
- **テスト時に実メールを送らない方法**: プレビュー環境では SMTP_USER/SMTP_PASS と
  RESEND_API_KEY を設定しない（送信はスキップされ、予約は普通に動く）。

## 管理画面でできること

作品の登録・編集／公演回の作成・複製・編集／公開・非公開・受付停止・中止／
定員・受付期限の設定（確定人数未満への定員変更は不可）／予約人数と残席の確認／
予約者一覧・詳細／人数変更・キャンセル（枠が戻る）／電話・LINE受付分の手動登録
（定員チェックあり・確認メール送信可）／確認メール再送／リマインド設定・送信状況／
CSV出力（Excel対応・BOM付きUTF-8）。
予約履歴のある公演回は削除できない（中止にして履歴を残す）。

## セキュリティ

- 管理ページ・CSV・管理操作はすべて合言葉＋HttpOnly Cookie 認証。ログインは
  IPごとに10分5回で施錠（/contact 管理と共通の仕組み）。
- 予約者の個人情報は公開ページ・公開APIに一切出さない。完了画面のURLに載るのは
  予約番号だけで、番号から個人情報は引けない（照会APIは存在しない）。
- 入力はサーバー側で再検証。ハニーポット＋IPレート制限（1時間20件）で bot の
  大量申し込みを抑止。メール認証情報はサーバー側の環境変数のみでブラウザに出ない。
- Astro の Origin 検査（CSRF対策）が全 POST に効いている。

## 運用メモ

- 日時はすべて日本時間。公演回の「開催日時」「受付期限」は分単位。
- 公開中の公演がゼロのときは「現在受付中の公演はありません」＋貸切相談への導線が出る。
  貸切の相談導線（フォーム・LINE）は従来どおり残っている。
- テスト公演を作る場合は「非公開」のまま `/hacktale/reservation/<ID>/` を直接開けば
  一般には見えない…ではなく、非公開の公演回はフォームも開けない仕様。テストは
  公開→予約→中止→（予約ゼロなら削除）の順で。
- 検証済みの受け入れ条件（2026-09-27、ローカルのモックKV/SMTPで全項目確認）:
  定員8に3名→残5／残席超過不可／残1席への同時申込は1件だけ確定／二重送信で重複なし／
  キャンセルで枠が戻る／満席・受付終了・中止は申込不可／完了・リマインド送信／
  キャンセル済みへのリマインドなし／メール失敗でも予約保持・再送可／スマホで完結／
  管理画面で一通り運用可。

- 立卓／流卓改修の検証（2026-09-27、モックKV/SMTP）: 対面は最少人数到達で自動開催決定し全員に開催案内1通／
  オンラインはDiscordリンク・振込先が未入力だと送信不可、入力後に一斉送信、再送信で重複なし／
  開催決定後の申し込みは開催案内のみ／見送りで受付停止・見送りメール送信／リマインドは開催決定済みの
  確定予約のみ（キャンセル済み・直前予約は除外）／最少人数に4件同時に達しても全員ちょうど1通・受付メールの混入なし。

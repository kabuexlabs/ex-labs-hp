## 2026-10-20 仮実装（本公開なし）

- **技術構成**：仕様書は「Next.js + Prisma + PostgreSQL の新規リポジトリ」を推奨しているが、仮実装は **既存サイト（Astro SSR + Vercel + Upstash Redis）の中に `/kampo/` として組み込んだ**。理由：新しい DB・Vercel プロジェクトの契約と設定なしに店頭で試せる、既存の合言葉ログイン・KV・デプロイの仕組みをそのまま使える。スコアリング・候補提示・安全確認は純粋関数、マスタは JSON のままなので、本番で独立リポジトリに移す場合もそのまま持ち出せる。
- **URL**：`/kampo/login/`（ログイン）→ `/kampo/check/new/`（受付）→ `/kampo/check/<id>/q/<n>/` → `/kampo/check/<id>/result/` → `/kampo/check/<id>/advice/<type>/`。スタッフは `/kampo/staff/pin/` → `/kampo/staff/` → `/kampo/staff/session/<id>/` → `/kampo/staff/customer/<id>/`。仕様書のパスに `/kampo` を前置しただけ。
- **保存先**：PostgreSQL ではなく Upstash Redis。顧客・セッション（提案を内包）・監査記録を `kampo:` プレフィックスで保存。提案（Proposal）は別テーブルにせずセッション JSON の中に持つ。
- **保持期限 3年**：セッション本体は Redis の TTL（EXPIREAT）で自動削除。索引側は `/kampo/staff/` を開いたときと `/api/kampo/purge`（CRON_SECRET）で掃除する。**Vercel Cron は登録していない**（Hobby プランの cron 枠 1日1回×2本を /api/yoyaku/reminder と /api/hacktale/reminder で使い切っているため）。
- **環境変数名**：他機能との衝突を避けて `KAMPO_` を前置（`KAMPO_PASSWORD`／`KAMPO_STAFF_PIN`／`KAMPO_SESSION_SECRET`／`KAMPO_SUPERVISOR_NAME`／`KAMPO_SUPERVISOR_BIO`／`KAMPO_STAFF_NAMES`／`KAMPO_RETENTION_YEARS`）。`KAMPO_PASSWORD` 未設定時は `YOYAKU_ADMIN_KEY` を流用、`KAMPO_STAFF_PIN` 未設定時は共通パスワードで代用（画面に注意表示）。
- **認証の Cookie**：iron-session ではなく、HMAC 署名つきの期限トークン（`kampo_s` 30日／`kampo_staff` 12時間、path=/kampo、httpOnly）。パスワードそのものは Cookie に入れない。ログイン失敗は同一IPから5回で10分ロック（既存の `login:rl:` を共用）。
- **レーダーチャート**：Recharts ではなくサーバー側で描く SVG（JS 不要・印刷でも同じ見え方）。
- **zod**：依存を増やさず手書きの検証（`src/lib/kampo/masters.ts`）。起動時に失敗したら例外でページを落とす。検証内容は仕様書どおり（B 全問に none、選択肢ID一意、keySigns 実在、weights のキー・範囲、タイプ8件、tips の参照）。
- **テスト**：Vitest/Playwright ではなく既存方式（`node --experimental-strip-types scripts/kampo-test.mjs`、`npm run check` に含む）。仕様書 第6節の検算例6件を含む。E2E は curl で主要導線を手動確認（Playwright は未導入）。
- **タイプ定義 JSON の形**：`data/types.json` は `{ "types": {8タイプ}, "tips": [条件つきの一言] }`。tips は `{ when: 選択肢ID, types: [TypeKey], text }`。
- **安全確認の「2週間以上」**：A4 の「1〜2週間」は含めず、「1か月以内・半年以内・それ以上」を2週間以上とみなす。「半年以上」は「それ以上」のみ。
- **誤字の修正**：仕様書の「山栩子」→「山梔子」、「目が冒えて」→「目が冴えて」、「苋類」→「芋類」、「涯しい」→「涼しい」、「捕き」→「取り除き」、「太溪」→「太渓」。文面はすべて JSON で薬剤師が直せる。
- **ロゴ・ブランド色**：`pharmacy.essence.fan` にこの環境から到達できず、ロゴは未取得。文字ロゴ「ESSENCE薬局」とアクセント色 `#2E7D6B`（仮）で実装。ロゴ画像とブランド色が分かれば `src/layouts/KampoLayout.astro` の `:root` と `.kp-brand` を差し替える。
- **アイコン・舌イラスト**：自作の簡素な SVG（`src/lib/kampo/icons.ts`、`public/assets/kampo/tongue/*.svg`）。参考サイトの素材は使っていない。
- **印刷**：`@media print` の A4 縦。結果画面の印刷では1ページ目にレーダーとカード、2ページ目以降に主体質の改善アドバイスを自動で付ける。
- **スタッフ名**：ユーザーアカウントは作らず、提案保存時に `KAMPO_STAFF_NAMES` の候補から選ぶ（未設定なら自由入力）。
- **監査記録**：`kampo:audit` に閲覧・保存・CSV書き出しを記録（最大5000件）。表示画面は未実装（仕様どおり初版なし）。
- **顧客の sex / ageBand**：A1・A2 の回答時に顧客レコードへ控える（履歴画面の表示用）。
- **性別を変更したとき**：B11・C3 の回答は捨てる（表示されなくなった設問の回答が採点・安全確認に混ざらないように）。
- **試験サイトの公開方法**：main には入れず、ブランチ `claude/jolly-mayer-khrsji` に push。Vercel のプレビューデプロイ URL（`*.vercel.app`）で試す。本公開（main へのマージ）はユーザー判断。

## 2026-10-24 漢方薬の選定を「主訴を起点とした二段階選定」に変更（ユーザー指示）

それまでは体質スコアと主訴を同時に点数化し、全処方から総合点で選んでいたため、体質のチェック内容が主訴と混ざって選定に影響していた。次の方式に置き換えた（src/lib/kampo/recommend.ts の selectFormulas）。

1. **STEP 1 主訴 → 候補群**：主訴（A3）ごとに「症状の詳細」（A3a〜A3m）を1画面ずつ聞き、選ばれた症状コードを、処方の**承認された効能・効果の諸症**（formulas.json の indications）に持つ漢方薬だけを候補にする。体質スコアを理由に主訴と関係のない漢方薬を候補へ加えることはしない。「高血圧や肥満に伴う便秘」のような条件つきの効能は、条件に当たる回答（requires）があるときだけ候補にする。
2. **STEP 2 体質との適合**：候補ごとに ①気血水（8タイプ。陰虚＝水不足）②寒熱（実熱・虚熱を区別）③虚実（承認基準のしばり「体力虚弱／中等度以下／中等度／中等度以上／充実」を範囲として持つ）④五臓（設問に五臓の重みを追加して集計）⑤主訴の詳細・随伴症状（使用目標に当たる回答 signs、ほかに選んだ主訴も効能に含むか）を照合し、適合度を出す。逆の虚実・逆の寒熱・虚熱に実熱向け、は「不適合」。
3. **STEP 3 選定**：主訴ごとに、安全性で除外されない「適合」のうち一致度が最も高いものを推薦する。同点は効能・効果の記載順（主な対象として先に挙がっている方）→ priority。先の主訴で選んだ漢方薬が次の主訴でも「適合」かつ僅差（0.1 以内）なら、それを優先して1つにまとめる（似た漢方薬の重複を避ける）。
4. **STEP 4 安全性**：contraindications に当たる安全フラグは除外。生薬×安全フラグの相談事項（甘草×高血圧、附子×心臓、大黄×授乳 など）、服用薬あり（名前未記入は情報不足）、治療中の病気、アレルギー歴、妊娠、安全確認の未回答は「要確認」とし、推薦を確定しない（来店客には「薬剤師が確認してからのご提案です」と表示）。
5. **STEP 5 推薦理由**：①主訴の候補になった理由（選んだ症状と承認効能の語）②体質に合う理由（実際の点数と回答。使用目標・漢方の考え方は別の欄）③ほかの候補との比較 ④服用前に確認すること、の順で出す。
6. **候補群の中に体質に合うものがなければ推薦しない**（来店客には「体質にはっきり合うものが見つかりませんでした。薬剤師が伺います」）。受診勧奨があるときも推薦しない。
7. 処方マスタを 36 → 68 処方に拡充し、承認効能（efficacy・indications）・使用目標（useTarget・strength）・漢方の考え方（action）を別の欄にした。効能・効果は一般用漢方製剤製造販売承認基準の記載に基づく初期値で、**全件 verified: false**（厚労省・PMDA の原文PDFにこの環境から接続できず、製品の添付文書や承認基準の抜粋で照合）。取り扱う製品の添付文書で薬剤師が確認したら true にする。照合で決め手がなかったもの：通導散のしばり（「体力中等度以上」か「比較的体力があり」か）、荊芥連翹湯の諸症の並び順、啓脾湯・黄耆建中湯の文言。
8. 来店客向けの漢方薬の表示は、主訴ごとに最大1件（同じ漢方薬はまとめる）。同じ注意生薬（甘草など）を含む漢方薬が複数並ぶときは重複の注意を出す。
9. 抜け毛・白髪は承認効能に当たる漢方薬がないため、候補なし（薬剤師に相談）とした。

## 2026-10-24（2）主訴の選択を3段階に変更（ユーザー指示「主訴選択画面の修正指示」）

それまでの主訴（A3）は「肌・髪」「月経・更年期」のように広い区分で、その次の画面（A3a〜A3m）で「赤く腫れる・化膿しやすいニキビ」のような**主訴と詳細が混ざった選択肢**を出していた。次の3段階に分けた（questions.json の K1・KA〜KH・KM・S*）。

1. **第1段階 大カテゴリー（K1）**：A 肌の悩み／B 髪・頭皮の悩み／C 年齢による見た目の変化／D 生理前・生理中の不調／E 更年期・ホルモン変化／F 疲れ・だるさ・体力低下／G 冷え・血行の悩み／H ストレス・気分の不調 の8つだけ。肌と髪、年齢による見た目の変化はそれぞれ独立。複数選択（最大3つ）。D は性別が男性なら出さない。
2. **第2段階 具体的な主訴（KA〜KH）**：選んだカテゴリーごとに1画面。ユーザー指定の一覧どおり（各「その他」は自由記入）。ここでは性質（赤い・繰り返す 等）を聞かない。
3. **いちばん改善したい主訴（KM）**：具体的な主訴を2つ以上選んだときだけ出し、1つに決める。選択肢は選んだ主訴（同じ名前が別カテゴリーにあればカテゴリー名を添える）。ほかの主訴は随伴症状として保存・利用する。
4. **第3段階 詳細問診（S*）**：いちばん改善したい主訴にだけ、1問1画面で2〜3問。主訴の選択肢の `detail`（テンプレート名）と設問の `showIf.mainDetail` で対応づけ、全117の主訴に42のテンプレート・100問を用意した（似た主訴は共通。例：ニキビ・吹き出物と生理前のニキビは acne、イライラ・怒りっぽさ・気分の浮き沈みは irritability）。見出しの `{main}` は主訴名に置き換える。ニキビ・肌の乾燥・抜け毛・顔のほてりはユーザー指定の問と選択肢をそのまま使い、ほかは同じ形（状態／部位・時期／悪化するとき・伴う症状）で作った。
5. 並び：性別・年代 → K1 → KA〜KH → KM → S* → A4（いつから・生活への影響）→ A5 → B（体質）→ C（安全）→ D（生活）。推薦は体質チェック完了後の結果画面だけで出す。
6. **詳細問診の回答の使い方**：
   - `symptoms` … 主訴の性質として候補群の抽出に加える（例：膿を持つニキビ → 化膿性皮膚疾患＝十味敗毒湯、肌の乾燥＋かゆみ → かゆみ）。
   - `also` … 随伴症状。候補群には加えず、効能・効果に含まれていれば適合度に加点（例：疲れ＋食欲がない → 補中益気湯の「食欲不振」）。ほかに選んだ主訴も同じ扱い。
   - `weights`／`organs` … 体質（気血水・五臓）の評価にも加える（多くは 0.5。表示されたテンプレートの設問だけ理論最大点に入る）。
   - 処方の `signs` に主訴・詳細問診の選択肢IDを入れ、使用目標に当たる回答として加点（主訴の詳細は別枠 0.1×件数・上限0.2。理由②の先頭に「【主訴の詳細】」で出す）。
7. **候補群の作り方**：主訴の `symptoms` を承認効能の語に対応づけた（例：ニキビ→にきび、生理前の不調→血の道症、生理痛→月経痛・月経困難、更年期の各症状→更年期障害＋その症状の語、動悸→動悸、息苦しさ→息切れ、顔のほてり→「顔や四肢のほてり」など）。更年期の「肌の乾燥」「抜け毛」は簡略更年期指数（SMI）の項目にないため、更年期障害の効能では拾わない。柴胡加竜骨牡蛎湯の「更年期神経症」は神経症として扱う（ほてりの主訴では候補にしない）。
8. **承認効能に当たる語がない主訴は候補なし**：毛穴・皮脂・ざらつき・ハリ・シワ・たるみ・ほうれい線・クマ・くすみ・顔色・抜け毛・薄毛・白髪・髪のパサつき・フケ・頭皮の乾燥など。体質スコアで別の漢方薬を当てはめることはせず、「効能・効果に持つ一般用の漢方薬がないため候補を挙げていません。薬剤師がお話を伺います」と表示する（詳細でかゆみ・湿疹・むくみなど効能に当たる症状が選ばれれば、その症状で候補群を作る）。
9. **途中の受診確認**：詳細問診の選択肢に `refer`（突然の激しい頭痛、手足のしびれ・ろれつ、胸の痛みを伴う動悸、安静時の息苦しさ、不正出血、黒い便 など）と `consult`（寝込むほどの生理痛、3か月以上来ない、2週間以上続く落ち込み、一部分だけ抜ける、体重減少 など）を持たせた。選んだ時点で画面に注意を表示し、回答は続けられる。refer は受診勧奨（来店客に漢方薬を出さない）、consult は注意フラグ＋推薦は「要確認」。
10. 処方マスタに症状コード（化膿しやすい皮膚の炎症・じんましん・赤ら顔／酒さ・のぼせ／ほてり・多汗・貧血・動悸・息切れ）と、それに当たる効能の語を追加した（いずれも efficacy 本文にある語）。旧 A3* を参照していた signs・requires は新しいIDに付け替えた。
11. 複数主訴の推薦は「いちばん改善したい主訴1つ」を中心に1件（以前の「主訴ごとに最大3件」はやめた）。CSV では詳細問診100問を列にせず「主訴の詳細」1列にまとめた。

## ① システムアーキテクチャ

- 画面：Astro SSR（既存の `/kampo/` 配下）。患者向け・薬剤師向けとも同じサイト内。
- 判定：`src/lib/kampo/` の純粋関数。回答 → 所見（findings.ts）→ 判定（assess.ts）→ 安全性（safety.ts）→ 候補（recommend.ts）→ 追加質問（staffq.ts）。外部 AI・機械学習は使わない。
- マスタ：`src/data/kampo/*.json`（薬剤師が直接編集・Git が変更履歴）。読み込み時に形式と確認状態を検証（masters.ts）。
- 保存：Upstash Redis（`kampo:` プレフィックス）。

## ③ 患者画面の遷移

1. 基本情報：性別 → 年代 → 月経の状況（男性以外）→ 妊娠・授乳（男性以外）
2. 安全性確認：いまの緊急症状 → 治療中の病気 → 服用中の薬の種類（検索・選択）→（漢方薬を選んだら）服用中の漢方薬（検索・選択）→ アレルギー → 漢方で体調を崩したこと →（はいなら）その漢方薬（検索・選択）→ そのときの症状
3. 主訴：カテゴリー（複数）→ カテゴリーごとの具体的主訴（複数）→（2つ以上なら）最も改善したい症状を1つ
4. 主訴別詳細問診：優先主訴に1問（複数選択）。安全上の確認が必要な主訴は、優先かどうかに関係なく確認の1問を追加
5. 経過：優先主訴はいつから・生活への影響
6. 共通体質問診：B1〜B13 の領域ごとに1問。すでに答えた所見の選択肢は出さない（全部答え済みなら問ごと出さない）。B7 むくみは関連する所見があるときだけ、B11 月経は月経がある（不規則を含む）ときだけ、B13 舌は受付で「ご自分で」のときだけ
7. 生活習慣（養生の一言用。判定には使わない）
8. 回答確認（修正は各設問へ戻る）→ 送信 → 送信完了（「スタッフにお声がけください」）

## ④ 薬剤師画面の遷移

送信完了画面の隠しボタン（長押し）→ PIN → 担当者画面。担当者画面は仕様書 §21 の順：
① 主訴（優先・その他・詳細・修飾情報）② 体質（主証・併存証・主訴関連の証・寒熱・虚実・五臓・整合性・根拠・未確認事項。低スコアの証は折りたたみ）③ 候補（4分類）④ 除外（理由・副作用歴・共通生薬・状態）
＋ 安全性（最上部）、追加質問（選択式。回答で再計算）、舌の観察（薬剤師）、副作用歴の原因生薬の記録、回答一覧、提案の保存。
説明用の結果画面（体質・養生のみ）は担当者画面から開く。

## ⑤ 条件分岐

設問の `trigger` で表示を決める：性別（sexNot）、月経状況（menses）、舌モード、カテゴリー選択（category）、主訴の選択（complaintSelected）、優先主訴（primary）、主訴の数（minComplaints）、所見（findingsPresent）、選択肢（chosen）。体質問診の選択肢は、それより前の回答で present／absent が決まっている所見を出さない（unknown は出す）。

## ⑥ 判定処理

- 所見：選んだ選択肢＝present、同じ問で表示されて選ばなかった選択肢＝absent、「特にない」＝表示した全選択肢 absent、「わからない」＝unknown、「回答しない」＝declined、表示していない＝not_asked。複数の情報源がある所見は、薬剤師の観察・回答 ＞ 患者の回答、同じ情報源内では present ＞ absent ＞ unknown ＞ declined。
- 気血水6証：所見重み 3/2/1。同一所見は証ごとに1回、相関所見はグループ内の最大点。暫定カットオフ（候補／強く示唆）気虚5/8・血虚5/7・気滞5/8・瘀血5/7・水滞5/8・陰虚5/8（開発テスト用の未検証値）。
- 主証：候補以上の証のうち、得点・独立した支持グループ数・重要所見（重み3）の取得・2位との差を見て決める。根拠不足（支持グループ2未満、重み3の所見なし、候補なし）や僅差（1点以内）は保留。
- 併存証：カットオフ以上／独立支持グループ2以上／主証と共通の所見を除いても候補点以上／重み3の所見あり／重要所見が未質問・不明でない、のすべて。
- 主訴関連の証：優先主訴とその詳細問診の所見だけで同じ計算をし、体質としての主証とは別に表示（優先しない）。
- 寒熱：寒・熱を別々に加点。各5点以上かつ独立グループ2以上で「傾向」。両方なら「寒熱混在の可能性」（部位・時間帯・随伴症状の確認を促す。上熱下寒とは判定しない）。どちらもなければ保留。虚熱／実熱は熱傾向のとき虚実・陰虚と合わせて「可能性」として出す。
- 虚実：虚・実を別々に所見の組み合わせ（独立グループ2以上）で評価。点数は補助表示。混在・保留あり。
- 五臓：主証・併存証を支持する present 所見のうち、その臓に関連するものが独立グループ2以上で「関連の可能性」。主証が保留なら五臓も保留。
- 整合性：寒熱・虚実の混在や保留、証と寒熱・虚実の組み合わせ規則（草案）で、整合／要確認／混在／判定保留。

## ⑦ 候補選定

STEP1 優先主訴の主訴対応マスタ（⑤）から候補を抽出 → STEP2 安全性 → STEP3 詳細症状・重要鑑別所見の一致／不一致 → STEP4 気血水・寒熱・虚実・五臓との適合 → STEP5 鑑別に必要な追加質問 → STEP6 分類。
分類：除外・対象外（安全性で除外）／安全性・情報確認待ち（安全性の確認待ち、または主訴対応・製品情報が未確認）／優先検討候補（主訴対応が確認済み、安全性に問題なし、詳細症状と体質が一致し不一致なし）／検討候補（それ以外）。
**現在は主訴対応がすべて草案、製品情報が未登録のため、除外以外はすべて「安全性・情報確認待ち」になる。**その中で参考順位（適合の高い順）と一致・不一致の根拠を表示する。

## ⑧ 安全性・生薬除外

- 緊急症状（いまの症状・主訴ごとの確認）→ 緊急対応優先：通常の候補提示を停止。
- 受診勧奨（生活への影響が大きく2週間以上 など）→ 全候補「薬剤師確認必要」以上。
- 妊娠・授乳・年齢・治療中の病気・併用薬・アレルギー・副作用歴・生薬×状態の注意（草案）・医薬品情報の確認状況を候補ごとに評価し、最も重い状態とすべての理由を保存。
- 副作用歴：副作用歴の漢方（処方）の構成生薬を取得 → 候補の構成生薬と照合 → 1種でも共通すれば除外。原因生薬未特定なら全構成生薬を暫定除外。薬剤師が原因生薬を資料つきで記録した場合も自動解除はしない（共通生薬を含む候補は「薬剤師確認必要」に残し、記録を表示）。構成が未確認（草案のみ）で共通生薬がなければ「安全性確認待ち」。漢方名がわからない場合も確認待ち。
- 併用漢方：共通生薬と注意（甘草の重複など）を表示。重複だけでは除外しない。

## ⑨ 未確定事項（草案として登録し、薬剤師・専門家の確認待ち）

- 全主訴の詳細問診の文言・選択肢（仕様書の例3件以外はすべて草案）
- 所見の重み（3/2/1）、相関グループ、カットオフ（仕様書の暫定値をそのまま使用）
- 寒熱・虚実・五臓・整合性の規則
- 主訴と処方の対応（一般用漢方製剤の承認基準の効能と使用目標を参考にした草案。医療用製品の効能は未確認）
- 処方の漢方医学的評価（草案）
- 構成生薬（処方の一般的な構成を草案として登録。製品ごとに異なる場合がある）
- 製品情報（効能・用法用量・禁忌・相互作用・副作用）：公式資料で未確認のため未登録
- 併用薬の注意規則（草案）
- 医薬品名の検索は、漢方は処方名、それ以外は薬の種類まで（医薬品名マスタは未整備）

## ⑩ 実装順序とテスト計画

実装順序：データモデル（masters・JSON）→ 患者向け UI → 所見・回答状態・重複防止・条件分岐 → 判定 → 薬剤師 UI と追加質問 → 処方・製品・生薬・評価・主訴対応のマスタ → 禁忌・副作用歴・生薬除外・併用 → 候補選定の統合 → テスト。
テスト（`npm run test:kampo`）：仕様書 §23 の全項目（問診①〜⑦、体質⑧〜⑮、処方⑯〜⑳、安全性10項目）をケースとして持つ。ほかに curl の E2E、Playwright の画面確認。
